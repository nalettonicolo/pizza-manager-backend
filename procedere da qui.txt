Architettura attuale
Frontend: React 18 + Vite; entry src/app/main.jsx → AppRouter (src/router/AppRouter.jsx).
Stato/auth: AuthProvider, TenantProvider, PvProvider, ThemeProvider (cartella src/app/contexts).
Dati principali: Supabase (client in src/lib/supabaseClient, tabelle tipo tenants, ordini, ecc.).
Deploy: script npm run build + Firebase Hosting (package.json); documentazione in DEPLOY_COMANDI.md.
Backend separato: cartella server/pizzeria-backend (Nest/Prisma) per parti aggiuntive; in documentazione si parla di API per turni e integrazioni, non come unico middleware per tutto il tenant.
Host: logica SaaS vs “negozio pubblico” in AppRouter: su pizzamanager.it / app.* / localhost si espone la piattaforma completa; su altri hostname la root va a PublicStore e rotte come /ordine per il cliente finale.

Cosa è già coperto (per area)

La mappa dettagliata admin vs roadmap è in docs/ARCHITETTURA_E_STATO.md (gap: lista ordini solo admin, KPI avanzati, billing, monitor, ecc.).

Piani e “servizi”: come sono collegati oggi
Catalogo servizi (src/features/superadmin/catalog/defaultCatalog.js): elenco servizi con ID stabili (ordini_cassa, stampa_comanda, ordini_online, tablet_ruoli, report_analisi, multi_sede, api_integrazioni, ecc.) e bundle Base / Pro / Enterprise / Full / Su misura (IDS_BASE, IDS_PRO, …).
Super Admin → Servizi e Piani: persistenza su localStorage (servicesStorage.js), non su DB centralizzato: utili per prezzi e packaging commerciale, ma non ancora enforcement automatico lato app.
Feature gate da piano tenant: usePlan (src/app/hooks/usePlan.js) con livelli FREE/TRIAL/PRO/ENTERPRISE è usato in modo molto limitato (es. Home.jsx); la maggior parte dell’accesso è per ruolo (ProtectedRoute), non per servizio acquistato.
Conclusione: i “servizi da includere nel piano” sono oggi definiti bene in catalogo e UI superadmin, ma non sono ancora il motore unico che abilita/disabilita moduli in produzione.
Recap per decidere cosa mettere nei piani
Usa il catalogo come lista canonica degli ID servizio; per ogni voce valuta:

Già implementato e usabile → candidato forte per un piano (es. ordini cassa, stampa comanda, ruoli operativi se coperti dalle route).
Parziale o solo commerciale (es. API, account manager, SLA) → piano alto o add-on, finché non c’è codice + enforcement.
In lavoro (pubblicazione dominio, menu per hostname) → allineare al servizio ordini online / vetrina quando la catena dominio → tenant sarà stabile.
Prossimo passo consigliato per allineare “piani” e prodotto:

decidere quali ID del defaultCatalog sono in scope per la release;
per ciascuno, indicare se serve solo etichetta commerciale o anche gate (nascondere route / chiamate API);
se serve il gate, pianificare dove leggerlo (colonna su tenants o tabella tenant_services + controllo in router o layout).
Se vuoi, nel messaggio successivo possiamo prendere il defaultCatalog riga per riga e classificarlo in Sì piano / Opzionale / Non ancora in base a come vuoi strutturare Base/Pro/Enterprise.
